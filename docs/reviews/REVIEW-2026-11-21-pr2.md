# Windows agent containment review

*Commit hashes, PR numbers and line numbers in this review refer to the history of the original private repository, which WAC was copied from with a fresh history.*

**Reviewed November 21, 2026.** The primary subject is PR #2 at `da9175c`. The review also covers the inherited host hook and the setup changes at `12adf3d`. The checked-out setup branch contains PR #2's head. The local `main` ref still points to the PR #1 merge, and GitHub's PR metadata available during this review showed PR #2 as open. Its merge into the hosted `main` remains unverified.

**Assessment.** A Hyper-V guest with no virtual network adapter, a standard host account, and a narrow broker is a sound starting design for Phase A. The implementation has several gaps that must be addressed before relying on it for untrusted workloads. The broker boots or resets a VM before proving its configuration, file transfers give SYSTEM access to paths influenced by unprivileged callers, and the host hook permits some host-side code execution. The newer setup branch adds a convenient provisioning entry point while leaving those runtime gaps in place.

## Findings

### PR #2 broker, transfers, and VM lifecycle

**1. High — Containment is checked after a VM can start.** For a stopped VM, `Gate` calls `Start` before checking adapters, integration settings, disks, or game-parent metadata. The real start path waits for PowerShell Direct, during which guest startup code can run. `reset` also stops, rebuilds, and restarts the VM before the gate. An eventual refusal cannot prevent the earlier boot. Check host-owned configuration before any start or reset side effect, validate the resulting VM after boot, and keep a diagnostic status command free of implicit recovery actions. Gate (`lab/gate.go:26` at `da9175c`) · Dispatch (`lab/broker.go:54` at `da9175c`) · Hyper-V scripts (`lab/hyperv_windows.go:67` at `da9175c`)

**2. High — Guest exports write as SYSTEM through a project-writable destination.** `pull` creates or reuses a timestamped directory under `lab-out` and starts the privileged copy before checking for reparse points. The output path is predictable and can be shared by requests in the same second. A copy or marking failure also leaves whatever has already reached the destination. Use a unique, broker-owned staging directory, validate the complete copy and mark every file there, then publish through an operation bounded by the caller's permissions. Treat Mark of the Web as file provenance and keep the execution policy independent of it. Pull and marking (`lab/broker.go:170` at `da9175c`) · PowerShell transfer (`lab/hyperv_windows.go:117` at `da9175c`)

**3. High — Recursive imports miss protected descendants and reopen paths as SYSTEM.** `push` checks whether the requested top-level name is within a protected path. A recursive copy of an ancestor can still include protected entries. The reparse-point walk and the subsequent PowerShell copy are separate operations over a tree the caller can change. Enforce the protected-path policy on each object and bind validation to the actual read. Collect files with the caller's permissions, then give the privileged service only the resulting approved input. Push and path walk (`lab/broker.go:147` at `da9175c`)

**4. Medium — The disk gate validates paths and metadata, with incomplete coverage of VM storage.** The check rejects extra hard-disk paths but accepts a subset of the recorded drives. The game-parent check reads the size and modification time of the recorded file without inspecting whether the attached differencing disk actually points to that parent. The packing script sets a read-only file attribute at an owner-supplied destination without establishing an owner-only ACL for that destination. Require the expected disk set and differencing chains, and place VHDs and their parent directories under verified owner/SYSTEM ACLs. Keep a trusted content-integrity record for the base images. Disk gate (`lab/gate.go:68` at `da9175c`) · Storage inventory (`lab/hyperv_windows.go:52` at `da9175c`) · Game disk packing (`install/pack-game-disk.ps1:59` at `da9175c`)

**5. Medium — The pipe ACL grants the client account permission to create server instances.** The owner's generic write permission includes `FILE_CREATE_PIPE_INSTANCE` on Windows. The first-instance flag checks the name at initial creation, and `lab-run` separately checks the server process's image path. Use explicit client rights, keep the namespace owned by the service for its lifetime, and validate the intended client/server identity model with a SYSTEM service and a standard user. The current pipe ACL admits its configured Windows identities across the broker's registered projects. The request's project name selects routing within that shared access. Pipe implementation (`lab/pipe_windows.go:43` at `da9175c`) · Broker project and VM resolution (`lab/broker.go:93` at `da9175c`) · [Microsoft named-pipe access rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)

**6. Medium — The broker lacks end-to-end request deadlines.** Pipe reads and writes use blocking I/O. There is a request size cap, but no per-connection read deadline, the close path flushes synchronously, and the per-VM lock can wait indefinitely. The run timeout starts after the gate. Transfers, the gate, and response delivery have no comparable deadline. Bound connections, queued work, operations, and output delivery. Verify that cancellation also ends the intended guest workload, since the current timeout directly controls the host PowerShell process. Pipe I/O (`lab/pipe_windows.go:92` at `da9175c`) · Broker timeouts (`lab/broker.go:122` at `da9175c`) · PowerShell process control (`lab/hyperv_windows.go:245` at `da9175c`)

**7. Medium — A passing probe has a narrower meaning than the status message.** The guest runs a handful of TCP and DNS probes, with a loopback and hostname positive control. The guest administrator can influence what the guest reports, and failed probes cover only the tested endpoints. For the modeled Phase B, the host gate checks the selected VM's own adapters but does not verify the other members of the switch or their uplinks. Base the Phase A decision on Hyper-V's authoritative configuration and use the guest probes for diagnostics. Before enabling Phase B, require the expected switch identity, VM membership, and peer topology. Gate and status (`lab/gate.go:42` at `da9175c`) · Guest probes (`lab/hyperv_windows.go:71` at `da9175c`) · [Hyper-V Virtual Switch](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/virtual-switch)

**8. Medium — The audit trail is incomplete and may retain application secrets.** The broker logs raw argv and paths and ignores write errors. Malformed pipe requests can fail before the logging path, and the available client PID helper is unused. The installed log directory is intended to be readable by local Users. The guest login credential follows a separate DPAPI path, but callers can pass other sensitive values in argv. Restrict log access, record the effective client/project/VM and result, omit or redact sensitive fields, and surface logging failures. Broker logging (`lab/broker.go:312` at `da9175c`) · Pipe request handling (`lab/pipe_windows.go:103` at `da9175c`) · Install ACLs (`install/install.ps1:22` at `da9175c`)

**9. Medium — `sync` can mix requests or discard a working guest checkout.** The client uses a fixed host and guest bundle name for each repository, with two independently gated broker calls. Concurrent syncs can interleave between the push and clone. The guest script also removes the existing checkout before the replacement has cloned successfully. Use a unique transfer identifier, clone into a fresh guest directory, and replace the existing checkout only after the new one is ready. Client sync (`cmd/lab-run/main.go:179` at `da9175c`)

### Existing host hook and project policy

**10. High — The host allowlist permits execution of editable Go tests.** The containment project enables `host_go`, has no protected source paths, and permits `go test`. A normal Go test run executes code from the editable working tree on the Windows host. Outside registered projects the hook deliberately uses broader rules, and the managed matcher covers only seven named tools. If the requirement is to prevent arbitrary agent-controlled host execution, enforce it through OS isolation or a separate build runner. For the current hook, document the host-code exception and explicitly inventory and restrict any host-capable tools that can run outside the matcher. Go policy (`hook/bash.go:473` at `da9175c`) · Containment project policy (`registry/projects/containment.json` at `da9175c`) · Tool matcher (`hook/hook.go:27` at `da9175c`) · [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)

**11. High — The approved Make target relies on shell interpretation of input.** The hook permits the game project's `add` target and validates the names of its `URL` and `NAME` variables. The adjacent game checkout's `Makefile` expands both values directly into a host shell recipe. The hook does not ensure that an accepted value remains one argument in that second shell. Move the operation behind an owner-controlled wrapper that validates the URL and destination and invokes Git with structured arguments. This finding is based on the local recipe in the adjacent checkout. Make policy (`hook/bash.go:373` at `da9175c`) · game project allowlist (`registry/projects/game.json` at `da9175c`)

**12. Medium — Git and file-write checks reason about path spelling and can select the wrong object.** The Git write check treats the current directory or Git's `-C` argument as a repository root. Git can discover an ancestor worktree with protected paths outside that directory. Edit, download, and project-scope checks also use lexical containment, so they do not prove where a Windows alias or reparse path leads. Resolve the actual Git worktree before applying write rules and prefer ACL-backed protection for owner-managed project files. Git working-directory handling (`hook/bash.go:197` at `da9175c`) · Protected Git paths (`hook/bash.go:319` at `da9175c`) · Edit checks (`hook/edit.go:19` at `da9175c`) · [Git worktree documentation](https://git-scm.com/docs/git-rev-parse)

### Installation and updates across both revisions

**13. High — The elevated bootstrap starts with code from the working clone.** PR #2 tells the owner to run the launcher elevated from any clone. The newer launcher starts unelevated and builds the PowerShell program it passes to `RunAs` in that same clone, including an interpolated repository parameter. The fresh checkout happens only after the bootstrap has selected the elevated code. Both launchers also assume their source-directory ACL change succeeds. Start from a protected owner-installed launcher, pass configuration as data, use a trusted source and toolchain, and verify the checkout location, owner, and effective ACL before building. The adjacent game project's `make lab` launcher uses the same bootstrap pattern. PR #2 updater (`install/update.ps1:3` at `da9175c`) · Setup branch updater (`install/update.ps1:7` at `12adf3d`) · Setup location check (`install/setup.ps1:16` at `12adf3d`)

**14. High — The setup branch authenticates a different file from the image it applies.** Setup picks the newest ISO by write time from the game project's downloads directory. Provisioning mounts it on the host, checks the Authenticode signature of `setup.exe`, and supplies a separate WIM or ESD to the image-apply operation. The signature establishes provenance for that executable alone. Pin a trusted digest of the full installation image or use separately authenticated image media from an owner-controlled location. Authenticate the chosen media before mounting it. ISO selection (`install/setup.ps1:41` at `12adf3d`) · ISO and image handling (`install/new-lab.ps1:50` at `12adf3d`) · [Microsoft Authenticode documentation](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/get-authenticodesignature)

**15. Medium — Installation can report completion after a failed containment check.** `install.ps1` invokes the hook and broker checks without inspecting their exit codes. The setup script also prints a warning on `lab-run status` failure and then prints “Done.” The hook check compares the entire permissions object against the generated baseline, even though install preserves other permission keys. Registry files are removed before their replacements are copied. Interrupted provisioning can leave a VM registered before setup has valid state or a ready guest. Give pending first-time provisioning an explicit state, validate the effective policy and ACLs, make replacement and recovery safe, and return a failure if a required final check fails. Install and checks (`install/install.ps1:41` at `da9175c`) · Hook check (`cmd/agent-hook/main.go:141` at `da9175c`) · Setup result handling (`install/setup.ps1:53` at `12adf3d`)

## Before relying on the lab

1. **Make the privilege boundaries enforceable.** Address VM start order, transfer permissions, the host-code execution exceptions, and installer/media provenance first.
2. **Verify the installed identities and controls on a disposable Windows Hyper-V VM.** Exercise the SYSTEM broker and the intended standard-user client, verify effective ACLs and Claude Code settings from a new session, and confirm the host rejects unsafe VM state before boot. Confirm a valid VM passes using harmless guest commands and files.
3. **Exercise failure and recovery.** Check that rejected transfers leave no published output, canceled work releases the broker and guest resources, installer failures are visible, and reset restores its documented disks while leaving the work disk intact.
4. **Keep later phases explicit.** Add independent game-process checks and a real Phase B topology test before extending the containment claim to a game binary or a server VM.
